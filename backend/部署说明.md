# v19 原 WorkBuddy 部署说明

本说明不代表已操作生产环境，更新包不含管理凭据。

1. **备份与基线。** 对照 original-files.sha256.json；存在后续更新时按差异合并。保留账号、IndexedDB 名称、旧表和附件。
2. **身份机制。** SQL 使用 PostgreSQL/PostgREST 的 request.jwt.claims.sub 和 authenticated/anon。确认 JWT 经网关验证后注入；若平台机制不同，只能适配官方验证身份接口，不信任客户端 UID。
3. **旧快照。** 确认 snapshots 真实所有者字段和 RLS；逐账号核对旧快照、新头表与本机记录。使用 SyncModel 合并后，经本人或受信管理迁移写入本人同步头。旧快照和附件不删除。
4. **安装。** 顺序 001_cloud_sync.sql → 002_rooms_v19.sql → 审核后 003_import_legacy_rooms.sql → 004_sync_compat.sql。003 仅迁移审核后的 u:UID，邀请码不变；匿名和未知归属留在旧表单独审核。新表使用 rigong_*_v19 前缀。
5. **权限。** 已认证用户只能执行 RPC，不能直接读写 v19 表。SECURITY DEFINER 函数固定 search_path，撤销 PUBLIC/anon 执行权，内部检查身份、成员资格、房主与本人授权。核实普通用户没有额外管理角色。
6. **旧设备。** 新旧房间表不双写。旧设备须刷新到 v19 后共同打卡；确认升级后，在原平台收紧旧房间写入口。旧表保留用于审计，不通过删表解决。
7. **认证和附件。** 沿用真实 publicConfig、手机号/微信登录、允许来源及 HTTPS；附件保持按账号私有。两个账号交叉访问必须被拒绝。
8. **生产验收。** 按 发给WorkBuddy.txt 完成 A/B/C 测试、实际手机号/微信、生产 CORS、移动端、PWA 安装和离线冷启动，再发布。tests/backend/tools/node_modules 不进入公开运行目录。
9. **版本。** U.VERSION=19、脚本/样式 ?v=19、SW rigongyizhu-v19 一致。临时预览链接按原项目支持的发布流程处理，明确返回同项目实际地址。
10. **回滚。** 参见根目录 回滚说明.md；保留新旧表、历史、附件和已撤回授权。
